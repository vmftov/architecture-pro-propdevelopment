# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. **Доступ к секретам:**
    - Кто:
        - "username": "kubernetes-admin",
        - "groups": ["kubeadm:cluster-admins", "system:authenticated"],
        - "sourceIPs": ["192.168.59.114"]
    - Где:
        - "namespace": "kube-system",
        - "name": "bootstrap-token-cssrrq"
    - Почему подозрительно:
        - Системный токен bootstrap-token используется для автоматической регистрации новых узлов в кластере. Запрос значения этого токена в обычном режиме работы кластера может говорить о попытке сканирования секретов.

2. **Привилегированные поды:**
    - Кто:
        - "username": "minikube-user",
        - "groups": ["system:masters", "system:authenticated"],
        - "sourceIPs": ["192.168.59.1"]
    - Комментарий:
        - Создание бессмысленного контейнера с повышенными правами. Возможно, попытка атаки типа Container Escape - попытка проникновения в кластер через привилегированный под путем обходм механизмов изоляции cgroups, namespaces.
            ```
            "name": "pwn",
            "image": "alpine",
            "command": ["sleep", "3600"],
            "securityContext": {
                "privileged": true
            }
            ```

3. **Использование kubectl exec в чужом поде:**
    - Кто:
        - В логах не найдено
    - Что делал:
        - С помощью exec в системном поде с нужными правами он мог бы изучить сеть и узнать какие ещё поды есть в кластере.
    - Комментарий:
        - В файле "audit-policy.yaml" нет настроек логирования ресурса "pods/exec", поэтому данное событие не попало в лог.

4. **Создание RoleBinding с правами cluster-admin:**
    - Кто:
        - "username": "minikube-user",
        - "groups": ["system:masters", "system:authenticated"],
        - "sourceIPs": ["192.168.59.1"]
    - К чему привело:
        - Сервисный аккаун, предназначенный для мониторинга был успешно повышен в правах до администратора кластера. Обычно аккаунты мониторинга привязываются ко всем подам работу которых необходимо отслеживать. Если бы злоумышленник смог получить доступ к такому поду, он смог бы получить доступ к большому числу секретов/ресурсов кластера и изменить их, нанеся серьезный ущерб компании или хотя бы продвинуться дальше к следующей уязвимости.

5. **Удаление audit-policy.yaml:**
    - Кто:
        - В логах не найдено
    - Возможные последствия:
        - Если бы подобная команда была выполнена, то злоумышленник смог бы отключить все политики безопасности, заданные в файле.
    - Комментарий:
        - kind: Policy является настройкой кластера, применяемой в момент инициализации. Её нельзя изменить или удалить командами apply/delete в процессе работы.

## Вывод

Обнаружены критические уязвимости. Слабые политики безопасности кластера позволяют злоумышленнику выполнять опасные действия.

Какие действия могли быть вредоносными:

- Создание привилегированного пода.
- Использование exec в чужом поде.
- Повышение сервисного аккаунта до администратора кластера.
- Удаление политик из audit-policy.yaml.

Что можно считать компрометацией кластера:

- Создание привилегированного пода.
- Повышение сервисного аккаунта до администратора кластера.

Какие ошибки допускает политика RBAC:

- Настройки RBAC позволили осуществить повышение прав сервисного аккаунта.
- Это явилось следствием нарушения принципа наименьших привилегий, когда обычному пользователю были назначены слишком широкие права на выполнение rolebinding.
- Настройки RBAC позволили создать привилегированный под.
- Отсутствие pods/exec в политиках аудита привело к пропуску важных событий.
