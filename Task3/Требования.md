# Имеющиеся ограничения

**В части биометрии для "умных" домофонов:**

- Закон 572-ФЗ запрещает хранить биометрию в собственных БД, предъявляет серьезные требования к безопасности при работе с биометрией и определяет крупные штрафы за несоблюдение законодательства.
- В компании имеется только 1 специалист по безопасности.
- У компании нет опыта работы с биометрическими данными.

**В части номеров автомобилей для шлагбаумов:**

- Номера автомобилей относятся к конфиденциальным данным.

# Описание решения

**В связи с указанными ограничениями принято решение:**

- передать ответственность за управление биометрией компании-партнёру;
- хранить номера автомобилей у себя согласно принципу Zero-Trust.

Таким образом удастся поддержать баланс. Конфиденциальные данные (номера автомобилей) не будут покидать внутренний контур безопасности компании. Компания-партнёр будет отвечать за работу с юридически сложными биометрическими данными. С компанией партнёром будет подписан договор.

# Типы передаваемых данных

**При регистрации пользователя в сервисах компании-партнёра, ей передаются:**

- Токенизированный идентификатор собственника для сопоставления данных пользователя на госуслугах с пользователем в системе при регистрации.
- Идентификатор домофона подъезда, в котором проживает собственник при регистрации.
- Идентификатор шлагбаума на въезде в закрытую территорию.

**В процессе работы, компании-партнёру передаются:**

- Управляющие команды на открытие шлагбаума.

**В процессе работы, от компании-партнёра передаются:**

- События об успешной аутентификации собственника в домофоне.
- Номер автомобиля, который пытается въехать на закрытую территорию.

Таким образом, персональные данные пользователя не будут передаваться компании-партнёру: вместо внутреннего идентификатора будет передаваться токен, а номера автомобилей будут проверяться внутри системы.

# Протоколы аутентификации и авторизации

Используется проприетарный протокол с bearer токенами для аутентификации пользователя.

- При аутентификации собственника в домофоне, в систему PropDevelopment передается событие о входе. Вместе с событием передается токен, содержащий идентификатор собственника, по которому API Gateway проверяет права доступа.
- При подъезде к шлагбауму, в систему PropDevelopment передается сообщение с номером атомобиля. Вместе с сообщением передается токен, содержащий идентификаторы собственника и шлагбаума, по которому API Gateway проверяет права доступа.

# Взаимодействие с сервисами компании-партнёра

### Аутентификация в домофоне

**Обычная ситуация:**

1. Если собственник захочет выполнить вход по биометрии, он должен будет подтвердить согласие в приложении.
2. Собственник будет перенаправлен на страницу компании-партнера, где он сможет подтвердить использование биометрии через гос-услуги. За логику работы отвечает BFF компании партнёра. При этом компании-партнёру передается токен идентификатора пользователя и идентификатор подъезда где установлен домофон.
3. Когда собственник подходит к домофону, за его аутентификацию отвечает компания-партнёр. Никакие системы компании PropDevelopment не принимают в этом участия.
4. В случае успеха, в систему PropDevelopment передается событие о входе собственника.
5. Сообщение аутентифицируется в API Gateway, которое запрашивает актуальные данные из CRM или кэша.
6. В случае успеха, сообщение регистрируется в БД.
7. Если собственник не найден, фиксируется попытка неавторизованного доступа.

**Ситуация с отсутствием интернета:**

- При отсутствии интернета данные о входе собственника могут передаваться в систему PropDevelopment с задержкой. Сам вход будет осуществлен, т.к. авторизация в системе PropDevelopment не требуется. При отсутствии связи с сервисами компании-партнера, предусмотрен резервный вход по карте или магнитному ключу.

### Въезд через шлагбаум

**По номеру автомобиля:**

1. Если собственник захочет въезжать через шлагбаум по номеру автомобиля, он будет должен заркгистрировать его в системе.
2. Когда собственник подъезжает к шлагбауму, камера определяет номер автомобиля и передает сообщение в систему PropDevelopment.
3. Сообщение аутентифицируется в API Gateway, которое запрашивает актуальные данные из CRM или кэша.
4. Сервис IoT сопоставляет номер автомобиля и номер шлагбаума, и если находит сообтетствие возвращает кманду на открытие шлагбаума.
5. Факт въезда фиксирвуется в БД.
6. Если собственник не найден, фиксируется попытка неавторизованного доступа.

**Через приложение:**

1. Если собственник не захочет въезжать через шлагбаум по номеру автомобиля, он может открыть шлагбаум нажав на кнопку в приложении.
2. Команда на открытие шлагбаума будет передана в сервисы компании-подрядчика.
3. Сервис компании-подрядчика передает сообщение в систему PropDevelopment.
4. Сообщение аутентифицируется в API Gateway, которое запрашивает актуальные данные из CRM.
5. Сервис IoT сопоставляет номер автомобиля и номер шлагбаума, и если находит сообтетствие возвращает кманду на открытие шлагбаума.
6. Факт въезда фиксирвуется в БД.
7. Если собственник не найден, фиксируется попытка неавторизованного доступа.

**Ситуация с отсутствием интернета:**

- При отсутствии интернета предусмотрен резервный въезд по карте или магнитному ключу.

# Требования к безопасности

**Общее:**

- Подписать/проверить договор/соглашение с требованием о соблюдении партнером 152-ФЗ, 572-ФЗ и других законов о защите персональных и биометрических данных.
- Регулярно проверять наличие/продление у партнёра необходимых лицензий и сертификатов ФСТЭК.
- Регулярно проводить аудиты безопасности.

**Управление доступом:**

- Обрабатывать только запросы, прошедшие аутентификацию и авторизацию, остальные только логировать.
- Использовать отдельный домен для сервисов по работе с IoT.
- Запретить доступ из сервисов, обслуживающих IoT к другим сервисам, кроме CRM на уровне NetworkPolicy Kubernetes.
- Ограничить доступ к API CRM на чтение ограниченного набора данных на основе атрибутов ABAC.

**Безопасность данных:**

- Никакие персональные данные собственников не должны передаваться в сервисы компании-партнёра.
- При регистрации пользователя во внешней системе использовать вместо внутреннего идентификатора - токен.
- Соединение с сервисами компании-партнёра должно быть защищено по протоколу SSL/TLS. Запрещать попытки соединения по незащищённому каналу и автоматически выдавать ошибку.
- Регулярно выполнять резервное копирование БД умного дома и логов.
- Проводить тестовые развертывания резервных копий БД.
- Вычислять хэши резерных копий для последующей быстрой проверки их целостности.

**Защита инфраструктуры:**

- Для обеспечения централизованного контроля безопасности все взаимодействия с сервисами компании-партнера должно осуществляться через API Gateway.
- Настроить в API Gateway аутентификацию и авторизацию запросов по ABAC.
- Настроить в API Gateway Rate Limiter для предотвращения DDoS атак.
- Использовать файрволл для проверки потоков данных на сетевом уровне.

**Управление инцидентами:**

- Логировать все успешные и неуспешные попытки входа в подъезд и проезда через шлагбаум для последующего анализа.
- Настроить обработку и визуализацию метрик с помощью Prometheus и Grafana для обнаружения инцидентов безопасности.
- Настроить оповещения специалиста по ИБ в случае обнаружения подозрительных ситуаций.
    > В идеале, необходимо внедрить SIEM систему. Передавать события аутентификации в SIEM систему для анализа попыток неавторизованного доступа на закрытую территорию. SIEM должна немедленно уведомлять ответственного специалиста по безопасности о таких инцидентах. А также временно блокировать возможность дрступа по биометрии, в случае попыток взлома.
    >
    > Однако, в текущих условиях, внедрение кажется неэффективным из-за наличия только 1 специалиста по безопасности и отсутствия опыта работы с такими системами.
